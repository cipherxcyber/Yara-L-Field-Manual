How YARA-L thinks

Three ideas to hold before anything else makes sense

Idea #1: sections, not a pipeline

YARA-L is declarative and sectioned. You describe the pattern — what events, grouped how, over what window, subject to what threshold — and the engine decides how to execute it. There is no | pipe operator, and the order you write the filters in does not change the result.

The sections always mean the same thing, no matter how complex the query gets:

SectionJobSearchRules
metaWho wrote it, what it detects, severity—Required
eventsDeclare event variables and filter themRequired (header optional)Required
matchGroup-by keys + time windowOptionalRequired if multi-event
outcomeCompute aggregates and context variablesOptionalOptional
conditionThe threshold that decides if it firesOptionalRequired
dedup order limit selectPresentation of resultsYesNot available
optionsZero-value handling, alert suppressionYesYes
exportWrite detection output into a data table—Rules only

Idea #2: one schema, one table

In SecOps every log — CrowdStrike, Okta, CloudTrail, Windows, Zscaler — is parsed at ingest into one schema, the Unified Data Model (UDM). There is exactly one table. You scope by three metadata fields:

The scoping trioput these first in every query
// What kind of activity is this? (the normalized verb)
metadata.event_type = "PROCESS_LAUNCH"

// Which product/vendor produced it? (survives re-parsing)
metadata.vendor_name = "Microsoft"
metadata.product_name = "Microsoft-Windows-Sysmon"

// The ingestion label — coarser, but cheap and reliable
metadata.log_type = "WINEVTLOG"

// The vendor's own native event code, unnormalized
metadata.product_event_type = "4624"
The single most useful habit

Always lead with metadata.event_type or metadata.log_type. Without one of them your query is a full scan of every event in the tenant, and a rule that scans everything is a rule that times out.

Idea #3: one language for searching and detecting

The same YARA-L you type into the Search bar is the language rules are written in. That is useful: you prototype in Search where feedback is instant, then promote the working logic into a rule by wrapping it in rule name { }, adding meta, prefixing fields with an event variable, and adding a condition. The differences are small and worth memorizing now:

Sliding windows (after / before)Not supportedSupported

A first complete rule

"Show me failed logins for a user, more than five in ten minutes." Here is that as a YARA-L rule.

The whole rule
rule failed_logins_burst {

  meta:
    author = "you"
    description = "More than 5 failed logins for one user in 10 minutes."
    severity = "Medium"

  events:
    $e.metadata.event_type = "USER_LOGIN"
    $e.security_result.action = "BLOCK"
    $e.target.user.userid != ""
    $user = $e.target.user.userid

  match:
    $user over 10m

  outcome:
    $failed_count = count_distinct($e.metadata.id)

  condition:
    #e > 5
}

Read it bottom-up and it clicks: #e is "how many $e events landed in this group", $user over 10m groups those events per user in 10-minute windows, and events is the filter. The idea to hold on to is the split between #e (a count of events) and $e (the existence of at least one).

Grouped fields: the "I don't care which field" shortcut

An IP can appear in a dozen UDM fields depending on the log source. Grouped fields are aliases that hit all of them at once — perfect for a first-pass IOC sweep during triage, though they are slower than naming the precise field. They work in Search (and in rules' events section), with regex and nocase.

Grouped field sweepthe triage one-liner
// Every principal/target/src/observer/intermediary/artifact IP field at once
ip = "185.220.101.34"

// Combine with a precise field to narrow
ip = "185.220.101.34" AND metadata.event_type = "NETWORK_CONNECTION"

// Others available: user, hostname, domain, email, hash,
// file_path, process_id, namespace
hash = "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
user = "jsmith" AND metadata.event_type = "USER_LOGIN"

  metadata.product_event_type, metadata.event_type

Run that once for every new log source. It tells you which native event names became which metadata.event_type, and how many landed in a *_UNCATEGORIZED or GENERIC_EVENT bucket that your event-type filters will never see.

Timestamps: event time vs. ingest time

UDM carries multiple timestamps, and picking the wrong one breaks latency-sensitive rules and retrohunts:

FieldMeaningWhen to use
metadata.event_timestamp.secondsWhen the activity actually happened on the endpoint/cloudDefault for match windows, ordering, and off-hours logic.
metadata.ingested_timestamp.secondsWhen Google SecOps received the logMeasuring parser/collector lag or hunting delayed telemetry.
metadata.collected_timestamp.secondsWhen the forwarder/agent picked up the logDiagnosing local agent buffering vs. network transport delay.
Zero values, not nulls

This trips up almost everyone. An uninitialized UDM string field is "", not null. An int is 0. An enum is "UNKNOWN_ACTION". That means count_distinct() counts empty strings as a real distinct value, array_distinct() returns [""] which renders as [Unknown], and joining two absent fields makes them "equal". The fix is always the same: add an explicit != "" filter in events.

UDM Search fundamentals

The filtering layer — where you will spend 80% of your alert time

A search expression is field, operator, value. No events: header needed, no event variable needed. Newlines and AND are interchangeable. Comments use // and /* */.

OperatorUseExample
= !=Equality on strings, ints, bools, enumstarget.port != 443
> < >= <=Numeric and timestamp comparisonnetwork.sent_bytes > 10000000
/regex/RE2 regex, no anchors impliedprincipal.ip = /^10\./
nocaseCase-insensitive; works on strings and regexprincipal.hostname = "JDoe" nocase
AND OR NOTBoolean, with parentheses for grouping(A OR B) AND NOT C
in %listReference list / data table membershipprincipal.ip in cidr %corp_ranges
field[key]Access additional.fields and labelsadditional.fields["pod_name"] = "kube-scheduler"
There is no LIKE and no *

YARA-L has no wildcard operator. Substring matching is regex: = /psexec/, or the function form strings.contains(field, "psexec"). Anchors are yours to add: /\\psexec\.exe$/. The engine uses RE2, so no backreferences and no lookaround.

Value formatting rules that will bite you

Getting literals right
// Strings: double quotes. Enums: ALL CAPS, still quoted.
metadata.event_type = "NETWORK_CONNECTION"
metadata.product_name = "Google Cloud VPC Flow Logs"

// Integers and floats: no quotes
target.port = 443
security_result.about.asset.vulnerabilities.cvss_base_score >= 9.0

// Booleans: bare true/false
security_result.is_alert = true
network.dns.response = true

// Backslashes and quotes need escaping inside strings
principal.process.file.full_path = "C:\\Windows\\System32\\cmd.exe"
target.process.command_line = "cmd.exe /c \"c:\\program files\\a.exe\""

// Regex is cleaner for Windows paths — and case-insensitive by habit
target.process.file.full_path = /\\cmd\.exe$/ nocase

// "Field is populated at all"
additional.fields["pod_name"] != ""

The catch-all: /.*/

A field compared against /.*/ matches whatever the field holds. That makes it a neutral placeholder: the line stays in the query, does no filtering, and can be swapped for a real value later.

Catch-all regexa filter slot that passes everything
metadata.event_type = "USER_LOGIN"

// You don't have a value yet — keep the slot, filter nothing
target.user.userid = /.*/
principal.ip = /.*/

// Later, narrow one slot without restructuring the query
target.user.userid = /^svc-/ nocase

// "Any value, but there must be one" — note the + instead of *
principal.hostname = /.+/
  • Saved searches. Write each filterable field as its own line with /.*/ as the default. The search returns everything until someone replaces one slot with a specific pattern, and the rest of the query never has to change.
  • Templates during triage. Keep one query per alert type with every pivot field present as /.*/, then fill in host, user or IP as you learn them.
  • It also matches empty. .* matches a zero-length string, and an unset UDM field is "", so /.*/ should pass events where the field is missing too. When you need the field to be populated, use /.+/ or != "". Confirm this on one field in your own tenant before you rely on it.
  • It is not free. Every regex is evaluated per event, so keep metadata.event_type or metadata.log_type as the first line and don't stack more catch-all slots than you will actually use.
  • Not for join or match keys in rules. A catch-all lets empty values through, which is exactly the empty-string join problem from Module 04.

Raw log search: your escape hatch

When the parser hasn't mapped the field you need — a brand-new product, a custom app log — you can search the original text. It is slower and returns raw records rather than UDM events, but during an incident it is often the fastest way to prove something exists.

Raw log search
raw = "mimikatz"
raw = /sekurlsa::logonpasswords/ nocase

// Find logs that failed to parse at all — a parser health check
raw = /./ AND parsed = false
Query hygiene that actually changes runtime

Order your filters most-selective-first. Prefer an exact field over a grouped field. Prefer metadata.log_type over a regex across command lines as your opening filter. Searches return up to 1M matching events (30K by default, adjustable in Search settings; 10,000 displayed in the Events table) and 10K stats rows, so if you are hitting the cap, narrow the time window rather than scrolling. Keep queries under 100 UDM fields.

Statistics and aggregation

match is your group-by, outcome is your aggregate list

Aggregation in YARA-L is split across sections: the group-by keys and the time bucket go in match, the aggregate functions go in outcome. Sorting and truncation go in order and limit.

UDM Searchtop source IPs by distinct users
metadata.log_type = "OKTA"
principal.user.userid != ""

match:
  principal.ip

outcome:
  $user_count = count_distinct(principal.user.userid)
  $users      = array_distinct(principal.user.userid)
  $countries  = array_distinct(principal.ip_geo_artifact.location.country_or_region)

order:
  $user_count desc

limit:
  20

The aggregate functions

FunctionReturns
count(expr)Rows in the group
count_distinct(expr)Distinct values in the group
sum · avg · min · max · stddevNumeric aggregates
array(expr)All values as a list
array_distinct(expr)Distinct values as a list
earliest(ts) · latest(ts)Boundary timestamps, microsecond precision

Arrays are truncated

array() and array_distinct() are truncated to 25 elements (chosen at random; array_distinct() deduplicates first). If an outcome array looks suspiciously short, that's why — and it's a reason to use count_distinct() for thresholds and arrays only for analyst context.

04

Joins, entity context and lists

Correlating two event shapes without a join command

This is where YARA-L stops looking like a filter language. There is no join keyword. Instead you declare two event variables and give them a shared placeholder variable. The engine infers the join.

The join primitive
// Assign the same placeholder from both sides — that IS the join key
$e1.principal.user.userid = $user
$e2.target.user.userid    = $user

// Transitive: because both bind to $ip, e1.source.ip = e2.target.ip
$e1.principal.ip = $ip
$e2.target.ip    = $ip

// Direct field comparison also works, but is less efficient
$login.target.user.userid = $download.principal.user.userid

// Force ordering without a sliding window — cheap and precise
$e1.metadata.event_timestamp.seconds < $e2.metadata.event_timestamp.seconds
Always kill the empty-string join

If $e1.principal.hostname and $e2.target.hostname are both absent, both are "", and the engine happily joins them — producing a cartesian product of unrelated events. Add $e1.principal.hostname != "" every single time you join on a field that isn't guaranteed present.

The entity graph: enrichment you join to, not look up

For enrichment, SecOps has the entity graph — a separate namespace, graph.*, holding users, assets, groups, IOCs and prevalence. You bring it into a query as just another event variable.

Entity context joinonly alert if the account is a Domain Admin
$login.metadata.event_type = "USER_LOGIN"
$login.security_result.action = "ALLOW"
$login.target.user.userid = $target_user

// Pull the user entity and test group membership
$user_ctx.graph.metadata.entity_type = "USER"
$user_ctx.graph.metadata.source_type = "ENTITY_CONTEXT"
$user_ctx.graph.entity.user.userid   = $target_user
any $user_ctx.graph.relations.entity.group.group_display_name = "Domain Admins"

any and all are how you reason about repeated fields. any $e.security_result.description != "" means "at least one of the descriptions is populated"; all requires every element to satisfy it. Without the keyword, YARA-L implicitly unnests the array and matches if any element does — so you rarely need any for a plain equality, but you do need it when you negate or when you want to preserve array indexes for a later aggregation.

Cross-index trap on repeated sub-messages

If an event has two security_result entries — entry 0 is category = "SOFTWARE_MALICIOUS" with action = "BLOCK", and entry 1 is category = "ACL_VIOLATION" with action = "ALLOW" — writing two separate lines for category and action will cross-match entry 0's category with entry 1's action. Wrap sibling fields of the same repeated message in group() so both predicates must hold on the same array element:

group($e.security_result.category = "SOFTWARE_MALICIOUS", $e.security_result.action = "ALLOW")

Entity context is time-bounded

ENTITY_CONTEXT records carry graph.metadata.interval.start_time.seconds and end_time.seconds. During live rule evaluation and retrohunts, SecOps aligns the event timestamp against the active entity snapshot at that moment — so if a user was added to Domain Admins yesterday, a retrohunt over last month won't falsely flag historical logins unless you also inspect current context.

Prevalence: built-in rarity scoring

Derived context gives you domain and asset prevalence without computing it yourself, so there is no first-seen table of your own to maintain.

Rare-domain join
$dns.metadata.event_type = "NETWORK_DNS"
$dns.network.dns.questions.name = $domain

$prev.graph.metadata.entity_type = "DOMAIN_NAME"
$prev.graph.metadata.source_type = "DERIVED_CONTEXT"
$prev.graph.entity.domain.name = $domain
$prev.graph.entity.domain.prevalence.day_count = 10
$prev.graph.entity.domain.prevalence.rolling_max <= 5
$prev.graph.entity.domain.prevalence.rolling_max > 0

Threat-intel matching: indicators are entities too

Indicators from a threat feed are stored in the entity graph as entities — a domain, an IP address, a file hash. You match them the same way you matched a user: join the event to the entity through a placeholder, and narrow the entity side to the feed you mean.

IOC joinDNS query for a domain on a threat feed
$e.metadata.event_type = "NETWORK_DNS"
$e.network.dns.questions.name = $hostname
$hostname != ""

// The indicator, as an entity. Replace the vendor with your feed's name.
$ioc.graph.metadata.entity_type = "DOMAIN_NAME"
$ioc.graph.metadata.vendor_name = "ET_PRO_IOC"
$ioc.graph.entity.hostname = $hostname

match:
  $hostname over 10m

condition:
  $e and $ioc
  • Other indicator types. For IP indicators use entity_type = "IP_ADDRESS" and join on graph.entity.ip; for hashes use "FILE" and graph.entity.file.sha256.
  • Always name the source. Filter on graph.metadata.vendor_name or product_name as well as entity_type. Google's own enrichment (Safe Browsing, VirusTotal, WHOIS, Google threat intelligence) arrives as entities too, identified by those same three fields, and an unscoped join matches all of them.
  • Raise fidelity with prevalence. Google's sample rule for this pattern adds the rare-domain join from the previous section, so it fires on a listed domain that almost nobody in the environment talks to.
  • An entity cannot anchor a sliding window. Use a hop window, or pivot on the event.

Lists and tables in Search

Both work in Search as well as rules. Reference lists are a flat list of values; data tables are columnar, so you can match different event fields against different columns of the same row.

List and table membership
// Reference list — three matching modes
$e.principal.hostname in %corp_hostnames
$e.principal.hostname in regex %suspicious_name_patterns
$e.principal.ip in cidr %corp_cidr_ranges

// Data table — note the .column suffix
$e.target.hostname in %badApps.hostname

// Negation and case handling

Joins in Search

The placeholder mechanics are the same outside rules, with three differences worth knowing.

  • The join goes through match. Search joins are statistical: the shared placeholder must appear in the match section, and you get grouped rows back. Search also offers joins without a match section that return the full events; check the current Search documentation for their limits.
  • The correlation window is capped. Up to 48 hours.
  • Three kinds are supported: event to event, event to entity, and data table to event.

How rules run: Live, Retrohunt, Test Rule, and Curated Detections

  • Live evaluation: Runs continuously on streaming data. Single-event rules evaluate near real-time; multi-event rules evaluate as their match windows close.
  • Test Rule (Rules Editor): Runs an unsaved draft against up to 2 weeks of historical data in seconds without creating persistent detections — ideal for syntax and noise checks before saving.
  • Retrohunt: Runs a saved rule backwards over historical UDM data (up to 90 days depending on retention/tier) and writes real detections to the database — your move when a new IOC or TTP lands mid-incident.
  • Enabled vs. Alerting toggles: Enabled controls whether the rule runs and generates detections; Alerting controls whether those detections become analyst-facing alerts (and forward to SOAR/SIEM queues). Keeping noisy or low-signal building-block rules Enabled = On, Alerting = Off feeds Risk Analytics and composite rules (Module 10) without paging anyone.
  • Curated Detections: Google Cloud Threat Intelligence (GCTI) managed rule sets. You cannot edit their YARA-L directly, but you can inspect their logic, apply Rule Exclusions, and consume their output in your own composite rules via detection.detection.rule_name.

Multi-event rules and windows

Three window types, and picking the wrong one is the #1 compile error

The moment a rule has more than one event variable, match becomes mandatory and must carry a time window. Which window type you choose changes both the semantics and whether the rule compiles at all.

TypeSyntaxBehaviourReach for it when
Hop $key over 30m Fixed-length, overlapping windows. The engine picks the overlap and alignment, so events near a boundary aren't lost. Default. Any "these things happened near each other" correlation. Max 48h.
Tumbling $key by 1h Fixed, non-overlapping blocks aligned to the clock. At most one detection per key per block; later matches in the same block are deduplicated. Evaluates even when the count is zero. "Once per user per hour" rate-limiting, and any absence detection. Min 1m, max 72h. Fires only after the block closes.
Sliding $key over 5m after $pivot
$key over 5m before $pivot		 Anchored to a pivot event, looking forward or backward. Enforces true ordering. Strict attack-chain sequencing. Rules only — unsupported in Search. More expensive; don't use it where a hop window would do.

Absence with no anchor event: tumbling windows

  
This is the case where the window type is not a preference but a requirement. A sliding or hop window needs an event to anchor it, so a condition of "count equals zero" produces a Variable Not Bounded compile error. Tumbling windows evaluate each fixed block regardless of whether anything landed in it.

rule log_source_missing_heartbeat {

  meta:

    Absence detections arrive late — by design

    Two counting traps
    
Repeated fields inflate counts. If target.ip holds two values, count($e.target.ip) returns 2 for a single event. Multiple event variables compound. With $e1 and $e2 in a rule, every (e1, e2) pair becomes an aggregation row, so count($e1.field) counts each e1 once per e2. The answer to both is the same: aggregate on the unique event ID — count_distinct($e1.metadata.id).

Reference lists and data tables

      
Where allowlists, threat feeds and business context live

    

  

  


  
Reference lists are flat — one column of values, typed as STRING, REGEX or CIDR. Data tables are relational — named columns you can match independently, and which rules can write back into. Reach for a reference list when one column is enough, and a data table when you need more.


  

  

    
All six membership forms


// ---- Reference lists (flat) ----
$e.principal.hostname in %approved_servers                 // STRING
$e.principal.hostname in regex %hacktool_name_patterns   // REGEX
$e.principal.ip in cidr %corporate_ranges                // CIDR

// ---- Data tables (columnar) ----
$e.target.hostname in %crown_jewels.hostname
$e.security_result.rule_name in regex %tuning_exceptions.pattern
$e.principal.ip in cidr %threat_feed.network_block

  


  
Multi-column matching: the real reason to use a data table

  
A single row can constrain several event fields at once — the equivalent of a multi-key lookup. This is how you express "this service account is allowed to hit this resource from this subnet, and nothing else is".


  

    
Row-based context join


$e.metadata.event_type = "NETWORK_CONNECTION"
$e.security_result.action = "ALLOW"

Allowlisting patterns that survive contact with reality

  

    
Exclusion patterns


// Negate membership — the standard tuning exit hatch
not $e.principal.process.file.full_path in regex %approved_lsass_readers

// Case-insensitive membership (STRING and REGEX lists only)
$e.principal.user.userid in %service_accounts nocase


  


  

    Hard limits — memorize these
    
Per rule: 10 in statements total, of which at most 5 may use regex and at most 5 may use cidr. Per search query: 7 total, 4 regex, 2 cidr. If you are hitting the ceiling, collapse several lists into one data table with a type column, or move the logic into the entity graph. Google's own pages currently disagree on these figures (some list 7 / 4 / 2 for every surface), so check the live reference before you build right up to the ceiling.

Behavioral baselines: metrics.*

  
SecOps pre-computes hourly and daily behavioral metrics per user, host and IP — authentication attempts, DNS queries, bytes sent, file executions and others. A metric function reads those rollups in the outcome section of a rule or a Search query, so a 30-day baseline costs one lookup, not a 30-day scan. A rule that calls one counts against the multi-event rule quota.

  
Every function takes named parameters, in any order:

  

  

    
ParameterMeaningValues

      period:1d, window:30d, metric:first_seen, agg:max,

Composite and multi-stage detections

      
Rules that consume other rules — the highest-leverage feature in the language

    

  

  


  
This is the payoff for the low-score, non-alerting rules from Module 07. A composite rule takes detections as its input instead of raw events, so you can write a dozen cheap "observation" rules that never page anyone, then a single high-confidence rule that fires only when three of them line up on the same host inside an hour.


  

  
Referencing a detection

  

    
Two ways inrule ID is the durable one


// By rule ID — preferred: IDs never change
$d.detection.detection.rule_id = "ru_e0d3f371-6832-4d20-b0ad-1f4e234acb2b"

// By name, exact or regex — convenient, but renames will break it
$d.detection.detection.rule_name = "Suspicious PowerShell Download Cradle"
$d.detection.detection.rule_name = /Credential Dumping/

// Read an outcome variable the upstream rule published (outcomes[] is shorthand; variables[] is full proto path)
$host = $d.detection.detection.outcomes["principal_hostname"]
// Legacy / typed proto equivalent: $d.detection.detection.variables["principal_hostname"].string_val

// Reach through to the original UDM events behind the detection
$domain = $d.detection.collection_elements.references.event.network.dns.questions.name

// The detection's own time window
$d.detection.time_window.start_time.seconds

  


  

    Prefer variables over collection elements
    
Reading detection.detection.variables["x"].string_val is more portable and cheaper than digging into collection_elements, because it works the same whether the upstream producer was your rule, a curated detection or an ingested alert. The design implication: publish a consistent set of outcome variable names across your rule library — always $principal_hostname, always $principal_user_userid — so composites can join on them without special-casing each producer.

  


  
A kill-chain composite

  

    
Composite rulethree weak signals on one host = one strong alert


rule composite_endpoint_intrusion_chain {

  meta:
    author      = "ir-team"
    description = "Suspicious execution, then credential access, then external egress on one host."
    severity    = "Critical"
    type        = "Alert"

  events:
    $exec.detection.detection.rule_name = /Suspicious Script Execution/
    $host = $exec.detection.detection.outcomes["principal_hostname"]

    $cred.detection.detection.rule_name = /LSASS Handle Access/
    $host = $cred.detection.detection.outcomes["principal_hostname"]

    $egress.detection.detection.rule_name = /Rare External Destination/
    $host = $egress.detection.detection.outcomes["principal_hostname"]

    $host != ""

  match:
    $host over 1h

  outcome:
    $risk_score           = 95
    $risk_entity_to_score = $host
    $stages               = array_distinct($exec.detection.detection.rule_name)

  condition:
    $exec and $cred and $egress

  options:
    suppression_window = 24h   // one alert per host per day
}

  


  

    Composites and window boundaries
    
Composite rules match a detection's time interval against the hop window, not a single point in time. A producer detection whose window straddles two adjacent hop windows will match both — deliberately, so partially overlapping chains aren't lost. The consequence is duplicate alerts at boundaries, and the fix is the suppression_window shown above. Keep the composite's match window at 48h or less.

A composite isn't limited to detections. Give each source its own event variable and join on shared context — a curated detection, plus your EDR telemetry, plus prevalence from the entity graph, in one rule:

Multi-stage queries: aggregating an aggregate

  
Sometimes you need a statistic of a statistic — hourly bytes per host, then the average and standard deviation across those hourly buckets, then hosts more than three deviations out. A stage block computes the inner aggregation; the root stage consumes its outcome variables by name.


  

    
Multi-stagehourly buckets, then a weekly average


stage bytes_per_host {
  metadata.event_type = "NETWORK_CONNECTION"
  principal.hostname != ""
  $host = principal.hostname

  match:
    $host by hour

  outcome:
    $bytes = cast.as_int(sum(network.sent_bytes))
}

// Root stage: reference the named stage's outputs
$host = $bytes_per_host.host

match:
  $host

outcome:
  $num_hour_buckets = count_distinct($bytes_per_host.window_start)
  $avg_hourly_bytes = avg($bytes_per_host.bytes)
  $peak_hourly      = max($bytes_per_host.bytes)

Tuning, performance and the pitfall list

      
Everything that will waste an afternoon if nobody warns you

    

  

  


  
Options

  

    
The options section


options:
  allow_zero_values  = true    // include empty/zero match placeholders (default false)
  suppression_window = 1h      // suppress repeat detections; a duration such as 5m or 1h

  

  
By default, placeholders whose value is empty or zero are dropped from the match grouping — which is almost always what you want, because it prevents the empty-string join disaster. Turn allow_zero_values on only when the absence of a value is itself the signal. suppression_window is your first stop for a rule that is correct but noisy: it rate-limits per matched entity rather than requiring you to weaken the logic. Multi-event rules suppress on their match variables; a single-event rule needs a $suppression_key outcome variable to say what "the same entity" means, otherwise every detection is suppressed for the window.


  
The nine things that bite


  
1. No event type filter

  
A rule whose first condition is a reference-list membership check scans every event in the tenant. Scope first, then check the list.

  


// slow — evaluates the list against everything
$e.target.ip in %suspicious_ips

// fast — scope, then check
$e.metadata.event_type = "NETWORK_DNS"
$e.target.ip in %suspicious_ips

  


  
2. Zero-value joins

  
Covered in Module 04 and worth repeating because it produces silently wrong results rather than an error. Every join field gets a != "" companion.


  
3. Enrichment is eventually consistent

  
GeoIP, WHOIS, Safe Browsing and VirusTotal values arrive after the event does. A rule that filters on ip_geo_artifact.* will miss very recent events until enrichment lands. Always pair the filter with an emptiness check so un-enriched events are excluded deliberately rather than matched by accident:

  


$e.principal.ip_geo_artifact.location.country_or_region != ""
$e.principal.ip_geo_artifact.location.country_or_region != "United States"

  


  
4. Repeated fields inflate count()

  
Assign to a placeholder and use count_distinct, or count metadata.id.

  


// wrong: an event with 2 target IPs counts as 2
$outbound = count($e.target.ip)

// right
$ip = $e.target.ip
$outbound = count_distinct($ip)

  


  
5. Array indexing in outcome

  


// does not compile
$dept = $e.principal.user.department[0]

// works
$dept = arrays.index_to_str(array($e.principal.user.department), 0)

  


  
6. Placeholders beat direct field comparison

  
Binding both sides to a shared placeholder is optimized as a join key. A direct $e1.field = $e2.field comparison is correct but slower — use it only when you also need an inequality, like the timestamp ordering trick.


  
7. Future-dated events are skipped

  
Multi-event rules will not produce detections for events whose timestamp is in the future. If a source has clock skew, those events are invisible to correlation rules — a parser or NTP problem masquerading as a detection gap.


  
8. Search results and rule results won't match exactly

  
A search over the same logic returns raw matching events; a rule returns detections, which are grouped, windowed and deduplicated. If a search shows 400 events and the rule produced 12 detections, that is usually correct behaviour, not a bug.


  
9. Event variable cap & multi-way join explosion

  
A rule can declare at most 10 event variables (including graph entity variables). Beyond the hard cap, joining 3 or more high-volume event variables in one rule creates a Cartesian product across matching tuples before outcome: runs — always constrain each event variable tightly by metadata.event_type or metadata.log_type before binding join placeholders.


  
A tuning workflow that holds up

  
    
    
  1. Prototype in Search over a narrow window. Instant feedback, no rule lifecycle to manage.
    2. 
    
  2. Add match and outcome and check the group counts are what you expect before there is any threshold.
    3. 
    
  3. Wrap it as a rule with type = "Hunt" and alerting off. Let it accumulate detections.
    4. 
    
  4. Retrohunt over 30 days to see the true noise profile rather than guessing.
    5. 
    
  5. Tune by exclusion list, not by weakening logic. A not ... in regex %exceptions clause keeps the detection intact and makes the exceptions auditable.
    6.

When a rule doesn't fire

      
A diagnosis order that finds the cause without guessing

    

  

  


  
"Search finds the events but the rule produced nothing" has a short list of causes. Work through them in this order; the early ones are the most common and the cheapest to check.


  
1. Is the rule able to run?

  
    
    
  • Live and within quota. A saved rule that isn't enabled does nothing. Multi-event rules have their own quota inside the total; the Rules Dashboard shows both counts.
    • 
    
  • No rule errors. A rule can save cleanly and still fail at run time. Check the rule's error view before anything else.
    • 
    
  • Recently created or edited. A new or modified rule can take about an hour before its first detections appear.
    • 
  


  
2. Has enough time passed?

  
Detections are never instant for multi-event rules. The delay is the sum of the run frequency, the match window and any buffers.

  

  

    
Rule typeRunsEarliest detection

    
      
Single-eventNear real time, as events arriveMinutes

      
Multi-event, window under 60 minutesEvery hour by default; can be set to every 10 minutesAfter the window has fully elapsed, at the next run

      
Multi-event, window up to 48 hoursEvery hourOne to two hours after the events arrive

      
Multi-event, window over 48 hoursLess often, scaled to the window (roughly a tenth of it; daily for multi-day windows)Up to a day

      
Any rule testing for absenceAs aboveAt least one extra hour

    
  

  


  

  
3. Did the data arrive late, or out of place in time?

  
    
    
  • Compare event time with ingested time on one of the events. If a log arrives after the run that covered its event time, it misses that run. Later catch-up runs re-evaluate the period, so the detection appears hours later, not never.
    • 
    
  • Time zone mistakes look like ingestion delay. A source that sends local time parsed as UTC is hours "late" on every event.
    • 
    
  • Future-dated events are skipped by multi-event rules. Clock skew on a source hides its events from correlation.
    • 
    
  • Enrichment lands after the event. A rule filtering on geolocation or other enriched fields can't match until enrichment arrives, and is re-evaluated when it does.
    • 
  


  
4. Is the logic matching what Search matched?

  
    
    
  • Zero values in match keys. Events where a match placeholder is empty are dropped from grouping unless allow_zero_values is set. If the field is often empty, the rule sees far fewer events than Search.
    • 
    
  • Repeated fields. Search and rules treat multi-value fields differently, and a negated condition on a repeated field needs any or all to mean what you intend.
    • 
    
  • Case. Search compares strings case-insensitively by default in some contexts; rules do not. Add nocase where case can vary.
    • 
    
  • Windows. Two events that are 31 minutes apart are not in the same 30-minute window, whatever the Search time picker showed.
    • 
  


  
5. Did it fire, and you are not seeing it?

  
    
    
  • Suppression and tumbling windows deliberately hide repeats: one detection per key per suppression window or per block.
    • 
    
  • The daily cap. A rule version stops at 10,000 detections per day. A noisy rule can hit the cap early and stay silent for the rest of the day.
    • 
    
  • Sampling in the UI. A detection shows at most 10 sample events per event variable. Ten events on screen does not mean ten events matched; read the count in outcome.
    • 
    
  • Alerting is off. The rule produces detections, which you can see on the rule's detections page, but no alerts.
    • 
  


  
6. Are you comparing like with like?

  

  

    
Way of runningSaves detectionsWhy results can differ

    
      
Test in the Rules EditorNoWindows may be aligned differently from live runs. Up to about two weeks of data.

      
RetrohuntYes, marked as retrohuntThe time range must be at least as long as the match window. Uses the reference lists and data tables as they are now, not as they were.

      
LiveYesSees data as it arrives, including late data and later enrichment.

    
  

  


  

    The two-minute version
    
Take one event that should have matched. Paste the rule's events lines into Search, minus the $e. prefix, over a window around that event. Remove lines one at a time until the event appears. The last line you removed is the cause.

Window selection, in one card

  

  

    
If you need…UseBecause

    
      
"N of these happened close together"$key over 30mHop windows overlap, so nothing falls through a boundary. This is the default; reach for it unless you have a reason not to.

      
"At most one alert per entity per hour"$key by 1hTumbling windows deduplicate: first match in the block wins, the rest are dropped.

      
"This did NOT happen"$key by 24h + $count = 0Only tumbling windows evaluate empty blocks. Anything else gives you Variable Not Bounded.

      
"B must follow A, strictly"$key over 5m after $aSliding window anchored on the pivot. Rules only.

      
"What happened just before this alert?"$key over 10m before $alertBackward sliding window — root-cause analysis.

      
Ordering without the cost of a sliding window$a.metadata.event_timestamp.seconds < $b....seconds inside a hop windowCheaper, and usually sufficient.

    3. 
    
  3. Prefix every field with an event variable: metadata.event_type becomes $e.metadata.event_type.
    4. 
    
  4. Add != "" guards on every placeholder used as a join or match key.
    5. 
    
  5. Confirm the match window type matches the semantics you want (see the card above).
    6.

    7.

Glossary

  

  

    
TermMeaning

    
      
UDMUnified Data Model. The single schema every log is parsed into.

      
Event variable$e. A name for a set of events that satisfy the filters written against it.

      
Placeholder$user. A name bound to a field value. Binding the same placeholder from two event variables is a join.

      
Match variableA placeholder listed in match. Events are grouped by its value.

      
Outcome variableA value computed in outcome and stored on the detection.

      
Bounded / unboundedA bounded condition requires the event to exist ($e, #e > 0). An unbounded one allows it to be absent (!$e, #e = 0).

      
Hop windowover 30m. Overlapping fixed-length windows; the default.

      
Tumbling windowby 1h. Back-to-back blocks with no overlap; one detection per key per block.

      
Sliding windowover 5m after $e. A window anchored on a pivot event. Rules only.

      
Zero valueWhat an unset field holds: "", 0, or an UNKNOWN_* enum. There are no nulls.

      
Repeated fieldA field that holds several values, such as principal.ip. Rules evaluate one row per value.

      
Grouped fieldA Search alias such as ip or user that covers every UDM field of that kind.

      
Entity graphStored context about users, assets, domains, IPs and files, queried through graph.*.

      
Reference listA one-column list of strings, regexes or CIDR ranges, used with in %list.

      
Data tableA multi-column table, used with in %table.column. Rules can write to it with export.

      
DetectionOne match of a rule. It becomes an alert only if alerting is on for the rule.

      
Composite ruleA rule whose input is other rules' detections.

      
Curated detectionA rule set written and maintained by Google.

      
RetrohuntRunning a saved rule over historical data. Detections are kept.

      
Suppression windowA period during which repeat detections for the same key are dropped.
